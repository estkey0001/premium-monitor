# 実装計画 V2（2026-10-02・案）

> **進み具合（2026-10-03）**: Phase 0（データの正確さ）・0.1（表示の信頼性）・0.2（二次流通の価格の意味）は完了。Phase 1 は未着手（ユーザーの指示待ち）。

前提: 段階B（新UIの外枠・HOME・runtime・照合）は本番で受け入れ済み（UI_PHASE_B_REVIEW_PASS）。
MIGRATION_PLAN.md の段階 C 以降を、合意済みデザインに合わせて組み直す。

## 方針

1. **誤情報を止めるのが先、UI は後。** 公開中の誤価格（DATA_CAPABILITY_AUDIT.md §0 の E1〜E7）は、UI を作り替えても直らない。Phase 0 として先に直す。
2. **データの作業と UI の作業を分ける。** UI は mock のデータで先に完成させ、データの準備ができたものから実データにつなぐ。データが無いものは「未取得」と正直に出す。
3. **既存の判定は壊さない。** collector・利益判定・TCG の判定は、Phase 0 の誤り修正を除いて変えない。新しい定義での計算は、新UIの adapter の中だけで行う。
4. **各 Phase の進め方**
   1. mock のデータで画面を作る
   2. 1440px と 390px で確認する（あわせて 768px も）
   3. 実データにつなぐ
   4. 照合（parity）と deploy-check を通す
   5. 独立レビューを受ける
   6. 本番で受け入れを確認する

## Phase 1 — HOME とナビゲーション

- HOME: 「ジャンルから探す」（スマホ / TCG / カメラ / ゲーム / PC / その他）と「目的から探す」（利益商品 / 抽選・予約 / 在庫再開 / せどりルート）。それぞれ確認できた件数を出す。補助リンクは、データがあるものだけ。
- ナビ: 目的の4つと HOME。「商品検索」は主導線から外す。
- URL の状態: `?ui=new&page=<目的>&category=<ジャンル>`。全ページで category を引き継ぎ、ジャンルの変更と HOME へ戻る導線をはっきりさせる。
- ジャンルの定義を1か所にまとめる（products.yaml の genre と TCG を合わせる）。
- データ: 件数だけなので、今あるデータで作れる（利益商品の件数は、新しい定義で「計算できた件数」を出す）。

## Phase 2 — 利益商品

- mock: OpportunityView のサンプル。状態ごとに1件ずつ用意する（UI_VIEW_MODEL_SPEC.md §8 の全状態を含める）。
- PC は表、モバイルはカード。ページ送り。並び替えは利益 / ROI / 更新。絞り込みはカテゴリ・新着（在庫復活・買取急騰はデータができてから）。一覧の中の小さな検索（商品名・型番）。
- 実データ: Phase 0 が終わった買取ルート（正規→買取、二次→買取）を、新しい利益の定義で出す。成約データが無い正規→二次は、「成約価格 未取得 / 想定利益 算出前」で出す。
- **データの前提**: Phase 0 が終わっていること。

## Phase 3 — 抽選・予約

- 段階Cの計画（抽選・販売の新UIへの移行）を、ここに統合する。runtime・lottery_card・照合はそのまま使う。
- カテゴリを横断する（TCG・スマホ・カメラ・ゲーム・その他）。分類は、すべて / 抽選受付中 / 今日締切 / 予約・発売待ち。
- 市場参考価格・想定利益は、成約データが無いあいだは「未取得」「算出前」。
- TCG 以外の予約・発売のデータは **NOT_IMPLEMENTED**。無ければ「予約・発売待ち」は TCG だけで出す。watchlist の推測値は使わない。

## Phase 4 — 在庫再開

- mock で画面を作る（購入可能 / 再開履歴すべて）。
- **データの前提**: restocked_at / last_checked_at / current_stock_state を別々に持つ形に作り直し、在庫を本番で監視すること（今は一般商品 0件）。DB が毎回作り直されるので、状態の履歴を exports に残す仕組みが要る。
- それまでは TCG だけを、TTL を閲覧時に判定し直したうえで出す。一般商品は「未取得」。

## Phase 5 — せどりルート

- RouteView（費用の内訳つき）。
- 正規→二次、二次→二次を優先する。**データの前提**:
  - 成約データ（期間・件数つき）
  - 出品の最安値・最高値
  - 同一商品の照合の一本化（ProductIdentityResolver を本番の経路に入れる）
- 今ある二次→買取などは、利用状況とデータ品質を見てから扱いを決める（消さない）。

## Phase 6 — 商品詳細

- ヘッダーと3つのタブ（仕入・売却先 / 価格推移 / 最近の変化）。
- 価格推移は、履歴のデータがそろうまで「未取得」。

## 受け入れの基準（各 Phase で共通）

- 1440px・768px・390px で、横のはみ出し 0、タップ領域 44px 以上、コンソールのエラー 0。
- 状態の表示: empty / stale / out of stock / unpublished / not collected / source conflict / invalid price / missing fee / missing shipping / insufficient sold samples が、mock でそれぞれ表示できる。
- 安全のルール: 偽の鮮度・偽の価格・推測の締切・偽の在庫・出品を成約として扱う・時刻の手動更新・根拠の無い「公式」の表現、のどれも無い（テストと deploy-check で確かめる）。
- 運営者向けの情報が一般の画面に出ない。
- 通常の URL では旧UIを変えない（段階 F まで）。
