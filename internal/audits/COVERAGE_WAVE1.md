## 2. Stage 0 — 台帳の状態（Foundation の Low を閉じる）

`ledger_state` を、実行をまたいだ保持の有無と、同じ実行の中の再生成を区別する値にした。

| 値 | 意味 |
|---|---|
| `NOT_AVAILABLE` | 台帳が無く、実行をまたいで保持する手段も無い（鍵なし）。初めて見た日はこの実行の中だけ |
| `NEW_THIS_RUN` | 保持する手段はあるが、前回の台帳が無い（初回・キャッシュのミス） |
| `REUSED_WITHIN_RUN` | 同じ実行の中の再生成が、最初の生成の台帳を読んだ（前回の実行からの引き継ぎではない） |
| `RESTORED_FROM_PREVIOUS_RUN` | 前回の実行の台帳を引き継いだ（暗号化したキャッシュ・手元の `.private`） |
| `CORRUPT` | 台帳が壊れていた。作り直した |

台帳に実行の識別子（`run_id`）を持たせ、CI は `GITHUB_RUN_ID` と試行番号、手元はプロセスごとに決める。`first_seen_scope` は
`RESTORED_FROM_PREVIOUS_RUN` のときだけ `ACROSS_RUNS`、それ以外は `THIS_RUN_ONLY`（偽の永続性を示さない）。ワークフローは、鍵が 32 文字以上のときだけ
`RESEARCH_LEDGER_PERSISTENCE=enabled` を出す。**`RESEARCH_LEDGER_KEY` はまだ設定していない**（運営者が決める）。

## 3. Stage A・C — 候補を消さない・買取起点の順位

- **上限超え（実データで rejected になる above_genre_max）で確定から外れた価格差を、高優先の調査として残す。急変（price_change*）は収集側で rejected にならないため、実データではこの経路に来ない（通常の観測として残る）**（`research_class = HIGH_PRIORITY_RESEARCH`）。
  品質ゲートで隔離された買取価格（`collector_report` の `suspicious_prices`）を、新しい観測として調査候補に入れる。理由は
  `ABOVE_GENRE_MAX`・`NEEDS_CORROBORATION`・`PRICE_SPIKE`。**確定にはならない。ジャンルの上限は自動で引き上げない**（人が検証してから）。
  足りないのが他店の裏付けだけなら優先度に加点（`only_corroboration_missing`）。価格が大きすぎるもの（`over_3x_official` など）は誤価格の疑いとして低優先のまま。
- **買取起点の発見の順位**: 識別子（JAN・メーカーの部品番号・型番コード）がある行だけを候補にする。**名前だけの行は候補にしない**（件数だけ数える）。
  同じ識別子の行（色違い）は1つにまとめ、候補 ID は店と識別子から決まる安定したもの。順位 = 識別の確かさ + 小売の価格を引ける見込み + 価格差の見込み
  （買取の高い順ではない）。小売の価格のヒントは、公式の発見（Apple の購入ページ由来の未登録商品の部品番号 → 価格）だけ。**正本への自動登録は 0**。

## 4. Stage B — 公式の価格の確認

47 商品の内訳（2026-10-24 の調査）: 確認済み 11・期限切れ 1・公式で販売終了 20・販売中で未確認 15。

- **追加できた 2 件**: Nikon Z9（JAN 4960759906168・ニコンダイレクトの購入ページ・送料の規定あり）と Canon EOS R6 Mark II（製品ページで JAN 4549292200508 を確認・購入ページの商品コード 5666C001・送料無料）。
  どちらも既存の取得器（`nikon_direct`・`canon_store`）で毎日再確認する（`RECHECK_TARGETS`）。公式の価格は設定値と大きくずれていた（Z9: 設定値 700,000 → 公式 772,200 など）。
- **追加しなかったもの**（理由つき）: Sony の 3 機種（型番だけで JAN が静的 HTML に無い・送料が不明・現在のパーサは在庫語「当日出荷」を読めない）／
  Zf（同じページに色違いの価格があり、登録の商品が黒の基本型かの確認が要る）／販売終了の 3 機種／取得できない店（Fujifilm モールは CI で 403・Leica は robots を取得できない）／Xbox（版の選択待ち）。
- **25 件以上に届かない理由**: 販売中で未確認の 15 件のうち、今回安全に確かめられたのは 7〜8 件、そのうち登録の条件（JAN または同一性・送料・再確認の手段）が揃ったのは 2 件。
  公式で販売終了の 20 件は、公式の価格を現在の仕入れ値にできない（確認済みに数えない）。25 件にするには、確認済みの定義の見直しか、正本の構成（販売終了品の扱い）の見直しが先。
- **公式で販売終了の商品**は、公式の価格を現在の仕入れ値にせず、**販売店の新品を仕入れ値にする別経路（`SECONDARY_TO_BUYBACK`）**で扱う（Foundation で実装済み）。今回は候補の一覧にするだけで、取得は増やしていない。

## 5. Stage D・E — スマホ・カメラの小売起点（監査のみ・実装なし）

公式の商品一覧から、正本に無い商品（型番）を発見できるか。取得は `polite` 経由・各ドメイン 6 回以内。利用規約は**どのブランドも未確認**（実装の前提条件）。

| ブランド | 判定 | 根拠 |
|---|---|---|
| Samsung（スマホ） | **実装候補（最有力）** | 一覧の JSON-LD（ItemList・Product・offers）に型番（`modelCode`）と価格。商品ページの `hasVariant[].sku` に容量別・色別の日本の型番 |
| Xiaomi（スマホ） | 次点 | 一覧の JSON-LD に名前と価格。型番は無い（同一性の根拠が弱い） |
| Google Pixel | 設計のみ | 一覧に価格が無く、商品ページは最安値だけ。型番なし |
| Xperia | 設計のみ | 構造化データ・価格が静的 HTML に無い（価格は Sony Store 側） |
| Canon（カメラ） | **実装候補（最有力）** | カテゴリページの行に商品コード・名前・税抜価格。既存の `canon_store` の再確認とつながる |
| Nikon（カメラ） | 次点 | カテゴリ・商品名・JAN・価格が静的 HTML。カテゴリ ID の列挙が先 |
| Fujifilm・RICOH・Sony（ILCE） | 設計のみ | 名前だけ（価格・型番が静的 HTML に無い）／JS 描画／一覧の URL が不明 |

実装の優先順位: Canon（約 250 行・テストの HTML あり）→ Samsung → Nikon。正本の自動登録はしない（候補まで）。

## 6. Stage F・G — TCG の取得元

| 売り場 | 結果 |
|---|---|
| **カードラボ** | **実装した**（`src/collectors/tcg/lottery/clabo.py`）。店舗ブログに抽選・抽選予約の告知が静的 HTML で載り、応募期間・当選発表・購入期間・商品名・価格が本文にある。robots 許可・規約に自動取得の禁止の記述なし。店舗ごとの抽選として扱い、応募は店舗の X のため `entry_url` は空（作らない）。実サイトで確認: 一覧 30 件・候補 26 件・詳細 3 件から店舗ごとの抽選 3 件 |
| エディオン | 見送り。公開のお知らせに TCG の告知が 0 件（最新は 2024 年） |
| セブンネット | 見送り。公開のお知らせ・キャンペーンに TCG の語が 0 件。告知ページが無い |
| TSUTAYA | 保留。サイト全体が保守で停止（再開は 2026/10/30 の予定）。保守明けに再調査 |
| あみあみ・ホビーサーチ | 実装不可。403（Cloudflare のボットチャレンジ）。回避しない |
| 駿河屋 | 実装の価値が低い。トレカの予約への入口が検索結果だけ |
| HMV&BOOKS online | **規約の判断待ち（保留）**。静的 HTML・日程が本文・robots 許可の 3 条件は満たすが、規約が私的利用の範囲を超える使用・商用目的の利用を制限している。公開 LP に載せる使い方が該当しうる。年 4 回ほどの告知で、10 月分は 0 件 |
| その他の専門店・量販店 | 403・告知なし・robots 取得不可のいずれか |

**目標（到達できるが未実装の取得元を 2 つ以上）は未達（1 つ）。** 指定の 3 売り場は、そもそも公開ページに TCG の告知が無い・サイトが停止しているため、実装しても実データが 1 件も出ない。
**取得の流れ（Stage G）**: 告知（候補の記事）→ 解析できたイベント → 日程が読めず要確認 → 受付中 を数え、受付中が 0 件でも「市場に無い」とは断定しない
（取得元の未実装・遮断・到達不能が 1 つでもあれば `NOT_PROVEN_MARKET_EMPTY`）。カードラボの追加で、これまで 0 件だった受付中の抽選が実データで見え始めた（収集の不足だった）。

## 7. Stage H — TCG の定価

公式の商品 API が商品 1 個の希望小売価格と明示したものだけ 15 件（変更なし）。**パック価格から BOX の定価は作らない。** 取れなかった日は前回の行を残す（`carried_over`）。

## 8. Stage I・J — 公開と非公開 / 公開成果物の商品単位データの一覧

現行の境界を維持（個別の候補・順位・商品ごとの調査の理由は `.private/research/`。公開は件数・網羅性・理由別の集計だけ）。
既存の公開成果物（観測・診断）から再計算できる限界は、既知の限界として維持する。**判断材料として、商品単位の価格・取得元・除外理由を含む公開ファイルを一覧にした**
（`scripts/inventory_public_raw_data.py`・出力は `PUBLIC_RAW_DATA_INVENTORY.md`。削除・変更はしない）。

## 9. Stage K — 速い系と遅い系の分離（設計のみ・実装なし）

GitHub の定時の実行は毎日 4〜5 時間遅れて始まる（実績 +4h41m〜+5h24m。cron を 17 分に変えても変わらない）ので、リアルタイムの用途には使わない。

| 区分 | 用途 | 前提 |
|---|---|---|
| Slow lane（日次・今の Daily LP Update） | 公式の価格・長期の買取・発見（小売起点・買取起点）・レポート・調査候補 | 遅れても害がない |
| Fast lane（将来） | 抽選の開始・先着・再販・買取の急騰 | GitHub の schedule を前提にしない。別の実行の仕組みが要る。取得の作法（robots・間隔・正直な User-Agent）の範囲での頻度の上限を先に決める。通知は受入の関門を通す（調査候補・取得元の候補は通知に流さない） |

## 10. 既存テストの時限爆弾の修正

`tests/test_phase28_review.py` の固定の日付（実行の日から 7 日で、CLI の「公式で見てから 7 日以内」の判定に落ちる）を、実行の日の前日からの相対値にした。
