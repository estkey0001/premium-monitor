# MIGRATION PLAN（移行計画）

新しい画面構成（`NEW_INFORMATION_ARCHITECTURE.md`）へ、**既存の画面を壊さずに**段階的に移る計画。

## 0. 前提

- LPは `src/content/daily_lp_generator.py`（約9,700行）の `_section_*` メソッドが組み立て、`scripts/build_public_lp.py` が `docs/` に出力する
- GitHub Actions `daily_lp.yml` が毎日（cron 03:00 UTC と手動実行）生成して、そのまま本番に出る。**push では動かない**が、生成物のコミットは本番に直接出る
- `scripts/deploy_check.py`（7,331行）は生成HTMLに特定の文字列・id・クラスが含まれるかを225か所で確認する。失敗すると workflow が止まる（fail-closed）
- バックエンド・AI・利益計算・TCG判定・collector は**どの段階でも変えない**

## 1. 移行のリスク

| # | リスク | 内容 | 対策 |
|---|---|---|---|
| R1 | タブ切り替えのJS | `activateTab(tabId)` は `data-tab` と `tab-<id>` の対応で動く。`activateCategory`・メーカーチップ・`href="#tab-xxx"` のクリックもこれに依存 | 新しい画面は新しいJSで動かし、旧タブのJSは段階Fまで残す |

| R3 | テスト | `tests/` に生成HTMLを文字列で確かめるテストがある（例: `tests/test_tcg_lottery.py` が `id="category-tcg-lottery"` 以降を見る） | 同上。既存テストは消さない |
| R4 | Playwright | Playwright は collector（買取価格の取得）にだけ使われ、UIの自動テストは無い | 画面の確認は手動＋ブラウザ計測。UIテストの導入は別途相談 |
| R5 | 計測 | `data-track` 属性は約510か所あるが、計測タグは現行HTMLに見当たらない | 新しい画面でも同じ名前で付ける。計測タグを入れるかは別判断 |
| R6 | 通知 | Discord/Telegram の通知内容はHTMLの外で作られる。通知本文にLPのアンカーが入っていれば切れる | 通知スクリプトの文中URLを段階Bの前に確認する |
| R7 | ディープリンク | 外部（note、SNS、通知）から `#tab-lottery`・`#category-pro-camera` などで来る可能性がある。ただし現行は**読み込み時にハッシュを見ていない**ので、今も直接は開けていない | 段階Bで「旧ハッシュ → 新しい画面」の読み替え表を入れる（今より良くなる方向） |
| R8 | Pagesの生成 | `build_public_lp.py` は LP と collector_report だけを出力する。`/admin/` を足すなら出力対象の追加が必要 | 段階Eで追加。`robots.txt`・sitemap も同時に直す |

| R10 | 自動実行との衝突 | 実行中の workflow と push が重なると、自動コミットが失敗する（2026-09 に発生済み） | push 前に `gh run list --status in_progress` を確認 |
| R11 | ページの重さ | 現行 461KB。新旧を両方入れると一時的に倍近くになる | 新画面は既存データの参照だけにし、HTMLの重複を避ける |
| R12 | 管理画面の公開 | 静的サイトなのでアクセス制限ができない | noindex・robots・ナビに出さない。秘密情報は今まで通り出さない |

## 2. 移行の段階

| 段階 | 名前 | やること | 一般ユーザーへの影響 | 終わりの条件 |
|---|---|---|---|---|
| A | 設計だけ | このドキュメント群を作る | なし | ユーザーが設計を承認 |
| B | 新しい外枠 | 状態・色の対応表、共通部品（バッジ・ボタン・空状態）、ボトムナビ、HOME、ハッシュ読み替えを追加。**初期は `?ui=new` のときだけ表示** | なし（旧画面のまま） | deploy-check・pytest が全部通る。`?ui=new` で HOME が出る |
| C | 抽選・販売の移行 | TCG抽選・販売・旧来の抽選を新しいカードで1つの並びに表示 | `?ui=new` のときだけ | 旧画面と件数が一致する確認を追加 |
| D | 利益商品の移行 | ランキング・せどり・初心者・Pro を利益商品（タブ＋かんたん/詳細）と商品検索・商品詳細に | `?ui=new` のときだけ | 旧画面と商品数・利益額が一致する |
| E | 管理画面の分離 | `/admin/` を作り、Health・監視元の表・警告バー・eBay設定方法・collector_report を移す | `?ui=new` で一般画面から消える | `/admin/` が noindex で出力される |
| F | 新画面を初期表示にする→旧UIの削除 | まず新画面を初期表示に切り替え、旧画面は `?ui=old` で見られるように残す。一定期間問題がなければ、旧DOMと旧チェックの削除を**個別に相談**する | あり | ユーザーの承認ごとに1つずつ |

**今の状態（2026-10-06・UI Phase 8）**: 段階Fの前半を済ませた。クエリなしの URL・`?ui=new`・`?ui=` に知らない値 は新UI、旧UIは **`?ui=legacy`** のときだけ（計画の `?ui=old` ではなく `legacy` にした）。表示は URL だけで決める（cookie・localStorage では切り替えない）。旧UIの DOM・旧チェックは**まだ削除していない**（削除は1件ずつ相談）。段階E（`/admin/` の分離）は未着手で、運営者向けの情報は旧表示の Health にある。アーカイブ（過去の LP）は旧UIのまま。

- 段階B〜Eでは**旧DOMに手を入れない**。新しい `_section_*` を足すだけにする
- 1つの段階は1つのPR（またはコミットのまとまり）にして、いつでも戻せるようにする
- 段階Fの削除は `REMOVE_CANDIDATE` の一覧から1件ずつ、毎回ユーザーの確認を取る

## 3. 構成の判断

| 論点 | 案 | 推奨 |
|---|---|---|
| ページを分けるか | (a) 1ページ＋ハッシュ切り替え（今と同じ） (b) 画面ごとに別HTML | **(a)**。今のJS・deploy-check・Pagesの出力をそのまま使える。`/admin/` だけ別HTML |
| 管理画面の置き場所 | (a) 静的 `/admin/` (b) 既存の Streamlit（`dashboard/`、20ページ。ローカル用） | **(a) を基本にし、詳しい作業は (b)**。公開サイトの状態は (a) で見られるようにし、データ編集などは今まで通り Streamlit |
| かんたん/詳細の保存 | (a) localStorage (b) URL | **両方**。URLが優先、無ければ localStorage、どちらも無ければ「かんたん」 |
| 生成コードの分け方 | 9,700行の1ファイルに足すか | 新しい画面は `src/content/ui/`（新規）に分け、`daily_lp_generator.py` からは呼び出すだけにする |

## 4. 機能の凍結（フィーチャーフリーズ）の推奨

**推奨: 段階B〜Dの間、新しい機能・新しい画面要素・新しい collector の追加を止める。**

理由:
- 旧画面に機能を足すと、新画面への移行対象が増え、件数の一致確認がずれる
- 9,700行の生成コードに旧・新の両方が増えると、レビューできなくなる

例外（凍結中でも受け付ける）:
- **急ぎの抽選の情報源**: 大型の抽選（新弾発売など）が始まり、監視元を追加しないと「応募すべき抽選」を取り逃がす場合。既存の仕組み（`src/tcg/lottery/registry` への登録、手動CSV）の範囲で行い、表示は既存のカードに乗せる
- 誤った情報の修正（異常値、終了した抽選が受付中に見えるなど）
- 取得の失敗の修正（既存の collector の修理）
- セキュリティ・個人情報の修正
