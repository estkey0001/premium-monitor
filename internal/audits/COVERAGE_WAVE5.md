# Coverage Wave 5 — 利益が出やすい市場の優先度（Profit-Dense Priority）

2026-10-29。Wave 4 の判定は PARTIAL（正の価格差 6・調査候補 10・official verified 16）。今回は「照会できる商品を増やす」より
「利益が出やすい市場特性の根拠を、調べる順番に反映する」を優先した。**AI の予測価格は使わない。確定（VERIFIED）にも actionable にもしない。**

## 1. 優先度のモデル（Stage A〜E / U）

`src/research/signals.py`。どのシグナルも**根拠が無ければ付けない**（推測しない）。点は並べ替えにだけ使い、状態は変えない。

| シグナル | 付く条件（根拠） | 付けないもの |
|---|---|---|
| 発売からの経過（NEW ≤30 日 / RECENT ≤90 日 / ESTABLISHED / UPCOMING / UNKNOWN） | 公式で確かめた発売日（TCG は定価の台帳の公式 API の発売日） | 発売日が無い・読めない → UNKNOWN（加点しない）。発売前 → UPCOMING（加点しない） |
| 限定・特別（limited / special / anniversary / exclusive / collaboration） | **公式の**商品名・販売ページに語があり、公式の URL がある | 買取店の名前・名前だけの推測・公式でない定価の台帳 |
| 供給の逼迫 | 公式で在庫なし（OUT_OF_STOCK）・複数の取得元で購入不可・抽選のみ・再販の告知・短い応募期間（48 時間以内） | **在庫が不明（UNKNOWN）は逼迫にしない**（件数だけ `stock_unknown_not_counted` に残す）。公式でない 1 つの取得元の在庫なし |
| 買取の勢い | 前回より 3% 以上上昇（前回の観測があるときだけ）・同じ品目の「買取 ÷ 小売」の中央値より高い（標本 3 件以上）・小売の 95% 以上 | 前回が無い・実行をまたいで引き継げていない・7 日超の前回・条件つきの値引き・誤価格の疑い |
| 価格差が正 | 同一性つきで小売の価格を引けて、買取が上回る | — |

- **誤価格の疑い（PRICE_ANOMALY_SUSPECTED）・上限超え・急変は点を 0 にし**、確定にしない（HIGH_PRIORITY_RESEARCH に残す既存の扱いのまま）。
- 前回の買取の価格は、`state.json` の `buyback_prices`（非公開）に残し、**実行をまたいで台帳を引き継げたとき（`RESTORED_FROM_PREVIOUS_RUN`）だけ**比べる。
  鍵（`RESEARCH_LEDGER_KEY`）が無い CI では常に比べない → **`buyback_rising_candidates` は 0 のまま。これは「上がっていない」ではなく「比べられない」**。
- 公開は件数だけ（`research_signals`: new_release / limited / supply_pressure / buyback_rising / positive_spread / active_tcg_priority / stock_unknown_not_counted）。
  個別のシグナル・点・前回の価格は非公開（`PRIVATE_KEYS`）。
- 待ち行列の並びは「選別の点 + シグナルの点」で、**全行から上位 50 件を選び直す**。`research_class`・`status` は変えない（テストで固定）。
  小売の取得先の選定（`run_lookups`）は選別の点だけで決まり、シグナルは効かない（シグナルは照会の結果から作るため。Wave 6 の候補）。
- **シグナルを付ける行は絞る**: 価格差が無いと分かった行（REJECTED）・選別が HIGH / MEDIUM でない行・買取の観測が 3 日超の行は 0 点（`not_eligible`）で、件数にも数えない。
  誤価格・条件つきの仕入れ値・識別が部分的・上限超え・急変・裏付け不足の行も 0 点。**正の価格差の点は、実際の小売の照会（`retail_lookup`）で引けた行だけ**（公式の発見のヒントは除く）。
- **在庫なし**は、公式の結果が `availability_state = OUT_OF_STOCK` のときだけ（価格が読めないだけの `NOT_PURCHASABLE` は逼迫にしない）。
- 初回の reviewer / auditor の指摘（Medium 各 3 件: 価格が読めないだけの行が在庫なしになる・REJECTED 行を件数に数える・TCG の優先件数が「抽選が開いているだけ」を数える・並べ替えが上位 50 件の中だけ）はすべて修正済み。

## 3. TCG（Stage L / N / O / Q）

`src/tcg/profit_dense.py`。

- 応募の終了が過ぎたイベントは、状態の文字列が受付中でも対象にしない。`active_tcg_priority` は「抽選が開いているだけ」では数えず、発売直後・限定・短い応募期間・再販・期限が近い・定価に結べた、のどれかの根拠を要する。
- **優先度**: 受付中の抽選 / 予約 / 再販 / 期限が近い / 短い応募期間 / 公式の発売日が新しい / 公式の商品名に限定の語、の点。
- **質（イベントごと）**: 商品・小売・応募開始・応募終了・当選発表・購入期間・公式 URL の 7 項目。**7 項目すべて揃わないイベントは actionable にしない**（`actionable_event`）。
  現状の受付中イベントは公式 URL（行動の URL）が 0 件なので、actionable は 0。
- **定価との結び付き**: イベントの `product_id` が、定価の台帳（公式 API で商品 1 個の希望小売価格が明示されたもの。15 件）にあり、`product_match = exact` のときだけ結ぶ。
  名前の近さでは結ばない。**利益の計算はしない**。
- **検知の間隔のシミュレーション（実装はしない）**: 実際の応募の期間（開始・終了が読めるイベント）に対し、24 / 12 / 6 / 3 時間ごとに見に行く場合の取りこぼしを、
  見に行く位相 12 通りの平均で数える。最初の観測までの待ち時間 = **定時の実行の遅れ 8.4 時間**（Wave 4 の実測: 開始の遅れ最大 6.4 時間 + TCG の取得までの所要 約 2 時間）+ 間隔の位相。
  間隔を短くしても 8.4 時間は縮まらない（縮められるのは間隔だけ）。

  現在のイベント 39 件（`exports/tcg/lotteries.json`）での結果:

  | 間隔 | 応募の期間中に一度も見つけられない | 応募の半分を失ってから見つける（平均） |
  |---|---|---|
  | 24 時間 | 0 | 3.3 件 |
  | 12 時間 | 0 | 0 |
  | 6 時間 | 0 | 0 |
  | 3 時間 | 0 | 0 |

  Wave 4 の「1 日 1 回の最悪（遅れ 32.4 時間）では約 48% のイベントが半分以上を失う」は最悪の位相の数字。今回は平均の位相。
  応募の期間が 48 時間以上のイベントが大半なので、**12 時間間隔なら現在のイベントはほぼ全部が半分以上残っているうちに見つかる**。ただし 1 日の応募（約 24 時間）が増えると 12 時間でも足りない（実行の遅れ 8.4 時間が支配する）。
- **TCG の取得元の追加（Stage M）**: 実装した取得元は 0。調査の結果:
  - セブンネット・エディオン: robots.txt は取得を許すが、公開の抽選の告知一覧ページが確認できない（商品ごとの応募ページ・会員限定の専用ページ）。一覧が無いものは取得器にしない（`config/tcg_source_candidates.yaml` に除外として記録）。
  - TSUTAYA: 2026/10/30 以降に再調査（robots は許可）。HMV: 規約の判断が先。
  - **TCG working は 9 のまま（+2 の目標は未達）**。

## 4. 実行時間（Stage R / S）

Wave 4 の手動 run: 約 2 時間 24 分。内訳（>1 分の step）: カメラ買取 28.7 分・TCG 収集 51.1 分・小売の照会 22.3 分・買取 13.7 分・公式の再確認 8.2 分・公式価格 6.0 分・発見 6.0 分・抽選 5.8 分。
同じドメインへは 60 秒以上の間隔（`polite`）があるので、**時間は「ドメインごとの取得数 × 間隔」の合計で決まる**。

- **小売の照会を取得器（= ドメイン）ごとに並列化**（`retail_lookup._fetch_all`）。各ドメインへの間隔は `polite` が従来どおり守る（ドメインあたりの頻度は変わらない）。
  逐次だと各取得器の待ちの合計（約 22 分）だったものが、最長の取得器（Apple の 6 ページ）の待ちになる見込み（約 6〜12 分）。
- **同一実行内の同じ URL を二度取らない**（`RunFetchCache`）。メモリだけ・取得した時のまま返す（取得時刻を新しくしない）。遮断（403）・失敗も繰り返さない。別の実行・別の日の値は使わない。
  記録に `http_actual` / `http_cache_hits` を残す。
- **TCG の収集（51 分）は変えていない**。取得元ごとの詳細の取得枠（40）が「前の取得元の実使用で後ろの枠が決まる」逐次の再配分になっているため、並列にするには取得器を「一覧 → 詳細」の 2 段に分ける必要がある（Wave 6 の候補）。
- 目標「2 時間以内」: 小売の照会の並列化だけで約 10〜16 分の短縮の見込み。**本番の実測は「本番確認」に記す。**

## 5. 公式の確認（Stage G / H）

- Canon の購入ページ（公式。polite 経由）を実際に確認: 2 機種のボディーとも、構造化データ・本文から現金の税込価格が読めた。納期の表示（数週間〜数ヶ月）があるが、
  **納期は在庫の根拠にしない**（Wave 3 の規則どおり UNKNOWN）。クーポン対象の表示があっても、表示価格は通常価格（現金）。
  → **登録はしなかった**。新しい正本の商品を 1 つ足すたびに、公式の再確認が毎日 1 ページ増える（同じドメインは 120 秒間隔）ので、実行時間の目標と衝突する。
  Wave 6 で「Canon の表の商品を、照会（小売の取得器）と公式の再確認で同じ取得結果を使い回す（`RunFetchCache` を再確認にも使う）」設計にしてからまとめて昇格する。
- Sony α7C R（ILCE-7CR）: 購入ページは **シルバー（/S）とブラック（/B）の 2 色が同じ価格**で、ページの JAN は 1 つだけ（どちらの色の JAN かがページから確定できない）。
  色ごとの JAN が確かめられないので**登録しなかった**（推測しない）。正本の定価は古い概算のまま「要確認」（実際の価格より低い。再確認が要る）。
- Sony FX3: 前回と同じく購入ページが移転（moved）。登録しない。
- **official verified は 16 のまま（目標 25+ は未達）**。
