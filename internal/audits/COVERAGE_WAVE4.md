# Market Research Coverage Expansion Wave 4 — 公平な取得枠・同一性の強化（2026-10-29）

Wave 3 の結論: Sony・Canon の取得器が本番で動かなかった（商品ごとにページを取る取得器の対象を待ち行列の上位 50 件から選んでいたため、Apple の候補が枠を占有した）。
Apple の識別は部品番号だけで `IDENTITY_PARTIAL` のまま高優先に上がらない。TCG の取得元は CI で遮断されるものがあった。確定の判定（eligibility）は変えていない。
Phase31 には進まない。iPhone 18 系は一括登録していない。

## 1. 公平な取得枠（`retail_lookup.allocate_budget`・Stage A）

- 商品ごとにページを取る取得器（Sony・Canon・Sofmap）の対象を、**待ち行列ではなく全候補**から選ぶ（取得器ごとに点の高い順・重複なし）
- 配分の規則（`HTTP_BUDGET = 24`・`ITEM_MIN = 3`）:
  1. 一覧を取る取得器（Apple 6 ページ・ニコン 2・Samsung 1）は全ページ取れるときだけ取る（途中の一覧で引かない）
  2. 商品ごとの取得器には、まず**全ブランドに 1 件ずつ**、次に最低枠（3 件）まで。予算が少なくても、対象があるブランドは 1 件は取る
  3. 余りは点の高い順に、取得器ごとの上限（Sony 4・Canon 5・Sofmap 3）まで。総数は予算を超えない
- Apple の候補が 100 件あっても、Sony・Canon の対象があれば最低 1 件は照会する（テスト `test_apple_demand_never_starves_sony_or_canon`・`test_run_lookups_reaches_sony_and_canon_even_when_apple_fills_the_queue`）
- 記録（非公開）に取得器ごとの件数（対応する候補・取った件数・取れたページ・一致・不一致）を残し、公開の集計には件数だけ出す（`retail_adapters`）

## 2. Apple の同一性（Stage B）

- 引き当ては部品番号の完全一致。そこに、**買取店の商品名と Apple 公式の商品名の世代（機種の行）・容量**の一致を結び付ける（両方読めて同じ → `attributes_verified`）
- 両方読めて**違う**（部品番号は合うが容量・世代が違う）→ `IDENTITY_MISMATCH`（一致にしない）。どちらかが読めない → 確認済みにしない（`IDENTITY_PARTIAL`）
- `IDENTITY_CONFIRMED`（部品番号 + 容量 + 世代）の候補は、価格差が正・仕入れ値が新しい・買取が新しいなら高優先にできる。在庫・送料・裏付けの不明は理由に残す（高優先を妨げない）
- **JAN は追加していない**（Apple 公式に JAN の一次根拠が無い。推測禁止）。色は記録だけ（表記が違うので条件にしない）。名前だけ・容量の推測は使わない

## 3. Canon・Sony の本番の起動（Stage D / E / F）

- Canon（JAN ↔ 商品コード 20 行）・Sony は、上の配分で必ず照会が起きる。本番の件数は最終報告
- Sony の色違い: 型番表記が色違い（`ILCE-9TEST/S`）のページは読まない。同じ型番のページの JAN と買取の JAN が違えば別の色として一致にしない。未知の在庫語を在庫ありと推測しない（既知の語だけ）
- official verified: Sony FX3 の購入ページが移転（moved）で読めず登録できない。Canon の表を official verified に昇格するには、価格・同一性・送料・販売状態が揃う必要があり、
  今回は購入ページの再確認を毎日の対象にしていない（Wave 5）

## 4. 仕入れ元の選択肢（Stage G / H / I / J）

| 経路 | 状態 |
|---|---|
| Yahoo!ショッピング 商品検索 API v3 | JAN で商品を引ける（`jan_code`）。アプリケーション ID（`YAHOO_SHOPPING_APP_ID`）が必須 → **PENDING_USER_CONFIGURATION**（鍵なし）。保存・再配布の条件は規約で確認してから（鍵の有無だけを判定し、値は保持・出力しない） |
| 楽天市場商品検索 API | アプリケーション ID（と新しいエンドポイントではアクセスキー）が必要 → **PENDING_USER_CONFIGURATION**。JAN 指定の可否・保存の条件は公式の仕様で未確認 |
| 公開の商品フィード・アフィリエイトの商品 API | 鍵・契約が要る（今回は調査のみ。実装なし） |
| ソフマップ | 詳細ページは静的で、JAN・型番・現金価格・ポイント・在庫が分けて読める。**一覧から発見できず、JAN → sku の規則も無い**ので、人が確かめた JAN ↔ sku の固定登録（`config/sofmap_products.yaml`）だけを取る（検索・一覧・推測 URL は使わない）。登録は 1 行（実ページで確認。在庫切れ → NOT_PURCHASABLE を確認済み）。登録を増やすのは人の作業 |
| 量販店（エディオン・コジマ・マップカメラ 等） | 静的取得が遮断（Wave 3 の調査）。回避しない |

- 仕入れの証拠（Stage I）は Wave 3 の `price_evidence` のまま: 現金・ポイント・クーポン・キャンペーン・通常価格を分け、確定の仕入れ値に使うのは条件なしの現金価格だけ。
  Samsung の一覧の価格は割引込みの可能性があるので高優先にしない（Stage J）。ソフマップの「お一人様 1 点まで」は数量限定（条件）として扱い、ポイントは現金から引かない

## 5. TCG（Stage M / N / O / P / Q）

  「商品販売期間」を購入期間のラベルに追加。**クラウド IP から取得できるかは手元では確かめられない** → CI で遮断されたら `BLOCKED`（WORKING に数えない・回避しない）
- 見送り: ポケモンカードストア/ポケモンセンター（運営元の規約が自動取得を禁止している系統）・OTO（1 店舗・月 1〜2 件・応募は店頭のみ）・TSUTAYA（保守中。2026/10/30 13:00 まで）・
  セブンネット・エディオン（Wave 3 までの調査のまま）・HMV（規約の判断待ち）
- **取得元の状態の分離**: LIST_OK（一覧を読めた）/ DETAIL_OK（詳細を読めた）/ BLOCKED（遮断。手元で取れても CI で 403 なら BLOCKED）/ PARSER_DEGRADED（構造が読めない）/ TRUNCATED（取りこぼし）。

- **取得枠の再配分**（`src/tcg/lottery/budget.py`）: 詳細ページの総数に上限（40）を置き、**枠の小さい取得元から先に取り、最後に残りを最大の取得元（カードラボ）へ渡す**。
  後ろの取得元の最低枠（4）は先に確保する。遮断で使わなかった枠もカードラボに回る。カードラボは上限 16 → 24、優先は応募中 > 期限が近い > 新しい告知

## 6. 検知の許容と Fast Lane の必要頻度（Stage P / Q。実装しない・数字だけ）

- `RESEARCH_LEDGER_KEY` は**今回も設定しない**（Secrets は私が設定できない）。`first_seen` は実行をまたいで保持されず、`ledger_state = NOT_AVAILABLE`・`first_seen_scope = THIS_RUN_ONLY` と表示される。
  設定する場合: 32 文字以上のランダムな値を `gh secret set RESEARCH_LEDGER_KEY`（値はログに出ない・暗号化したキャッシュだけに使われる）。設定すると初めて見た時刻を保持でき、検知の遅れを実測できる
- 定時の実行の遅れ（直近 12 回の schedule の開始。予定 12:17 JST）: **4.2〜6.4 時間（中央値 約 5.1 時間）**。実行の所要は約 1.1〜2 時間（Wave 3 の手動 run は約 2 時間）。→ 1 日 1 回だと、最悪で観測までに 約 32 時間（24 + 6.4 + 2）
- 現在の TCG イベント 31 件（応募の長さの中央値 60 時間・最短 48 時間）で、応募の**半分の期間が残るうちに見つける**条件（応募の長さ / 2 ≥ 観測の遅れ）を満たす割合:
  - 遅れ 12 時間: 31 / 31　　遅れ 24 時間: 23 / 31（応募終了が 23:59 のため最短が 47.98 時間）　　**遅れ 32.4 時間（1 日 1 回の最悪）: 15 / 31（約 48%）**
  - 再現: `exports/tcg/lotteries.json` の `items` を `src.tcg.event_quality.evaluate` に通し、各イベントの `application_duration_hours / 2 >= 遅れ` を数える
- 結論: **1 日 1 回では半数のイベントが半分以上の期間を失う**。12 時間間隔（1 日 2 回）+ 実行の遅れ（最大 6.4h + 所要 2h）なら、最短 48 時間のイベントでも半分（約 24 時間）が残る見込み（20.4 時間 ≲ 24 時間。端数の余裕は小さい）。
  Fast Lane の最低の頻度は **1 日 2 回（12 時間以内）**。TCG の取得だけを軽くした別の実行（詳細取得の少ない一覧の監視）にすれば、全体の約 2 時間の実行を 2 回走らせずに済む
