# Phase 19 — 今すぐ行動できるようになった利益商品の通知（dry-run）

作成: 2026-10-08。外部への送信（Discord・Telegram・webhook など）はユーザーの明示の許可まで行わない。eBay は外部の設定待ち。

## 1. 基準（Phase 18 の生成物 ccbf6b24）

| 指標 | 値 |
|---|---:|
| 確定の利益商品 | 2（PS5 Pro 在庫切れ・GR IV HDF 抽選終了） |
| 今すぐ行動できる | 0 |
| newly_actionable（診断） | 0 |

| 重複の抑制の記録 | 既存の suppression.json（種類と商品で24時間）だけ |
| CI の所要時間 | 68.5分 |

既存の通知の種類（scripts/generate_notifications.py）: NEW_MAIN・WATCH_TO_BUY・PRICE_DROP・PRICE_RISE・ROI_UP・ROI_DOWN・
HEALTH_ALERT・DATA_RECOVERED。どれも生成だけで、実際の送信はしていない（配信の状態は ready / pending の記録だけ）。
ワークフローの結果の通知（scripts/notify_workflow_result.py）だけが、Secrets があれば送る（今回は変えていない）。

## 2. 種類の選び方

WATCH_TO_BUY は AI の候補の buy_now（価格からの判断）の WATCH → BUY で、在庫・抽選の受付・購入ページを見ていない。
抽選・予約の受付の開始には意味が合わないので、種類 **ACTIONABLE_NOW** を1つ足した（優先度は WATCH_TO_BUY と同じ Critical、
配信先は既存のランクの表 `routing.RANK_CHANNELS["S"]`）。既存の種類の表（PRIORITY・_template）に登録した。

## 3. 流れと順序

通知の生成（13.7）は LP の生成（14）より前に動くが、今すぐ行動できるかは LP の生成の中の診断で決まる。
そこで、候補の生成は LP の生成の中で、診断を書いた直後・画面を作る前に行う（同じ実行の運営者向けの画面に結果を出す）。

公式の取得 → 正規化 → 利益の案件 → 今すぐ行動の診断 → **通知の候補 → 配信の直前の確認 → dry-run の配信の計画** → 画面・報告

既存の通知（13.7）の位置・入力は変えていない（他の種類への回帰なし）。

## 4. 規則（`src/notifiers/actionable.py`）

- 候補: 診断の行（判定の正本の結果）で行動できる商品のうち、台帳の「最後に通知した組み合わせ」と違うものだけ。
  利益・ROI・URL・締切は診断の行のまま（計算し直さない）
- 重複の抑制の組み合わせ（dedupe_key）: 商品・種類・状態・受付の識別（抽選・予約・先着は商品 ID|受付の開始|締切。
  開始・締切は時刻に直してから並べる。書式の違いだけで別の受付にしない）。通常販売は空
- re-arm: 通常販売の在庫切れ・販売終了（できないと確かめた状態）でだけ、通知済みの記録を消す。在庫未確認・更新待ち
  （確認できなかった）では消さない。抽選・予約・先着の受付終了でも消さない（ページの表示の揺れで同じ受付を2回通知しない）。
  別の受付（受付期間が違う）は新しい通知
- 抑制: 最後に通知できた組み合わせと同じとき（通常販売のできる → できる）と、通知できた受付と同じ受付のとき。通知できた
  抽選・予約・先着の受付は商品ごとの集合（notified_events。締切を過ぎたら消す・最大20件）で持ち、一般販売と行き来しても・
  表示が予約などに変わっても同じ受付を2回通知しない（同じ受付で抑制したときは、最後に通知できた一般販売の組み合わせを
  消さない）。基準日に受付中だった受付も集合に入れる。前の形式の台帳は通知済みの組み合わせの受付から集合を作る。抽選から
  一般販売（在庫あり）に変わったら新しい買い方として通知する。
  配信が失敗・止めたものは通知済みに入らないので出し直す
- 基準日: 台帳が無い・読めないときは候補を出さず、今の状態を通知済みとして記録する。前回の状態を見ていない商品
  （台帳に無い・前回は確定の利益から外れていた NOT_CONFIRMED）も、その商品の基準日として記録だけする
  （利益だけが変わって在庫ありのままの商品を「購入可能になりました」と通知しない）
- 配信の直前の確認（revalidate。生成を始めた時刻ではなく配信の時点の時刻で行う）: 行動できる種類・理由なし・確定の利益（confirmed かつ利益 > 0）・期限（until_ms）が未来・
  抽選などは締切が未来・公式の購入/申込のページ（actionability._official_url）・組み合わせの一致。外れたら配信しない
- 配信: dry-run（既定。NOTIFICATION_DRY_RUN が false のときだけ外れる）では送信の関数を呼ばない。dry-run でなくても
  送信の関数を渡していない（今回はどこからも渡さない）ので送らない。送信の関数を渡したときの再試行は、タイムアウト・429・5xx
  だけを最大3回、同じ識別子で行う
- 台帳の記録: 計画（dry-run）・送信できたものだけを通知済みにする。失敗・止めたものは次の実行で出し直す（送っていないので重複しない）

dry-run で計画したものも通知済みとして記録する（毎回同じ計画を出さない）。送信を有効にした日には、その時点で行動できる商品は
送らない（有効にした後の「できない → できる」から送る）。

- 実行する場所: CLI の generate-daily-lp（CI の「Generate daily LP」）だけ（`generate(notifications=True)`）。買取のプレ値の
  ジョブ（run-buyback-premium-check）の途中の LP の生成では台帳に触れない（1回の CI で2回判定して後の候補が消えないように。
  そのステップには Secrets がある）

## 5. 出力

- `exports/notifications/actionable/latest.json`: 今回の件数（newly_actionable・候補・抑制・計画・送信・失敗・止めた）と候補。
  どの診断から作ったか（diagnostics_generated_at）。生成に失敗したら failed を書く（前回の件数を今回のものとして読ませない。
  台帳は変えない。deploy-check #855 は failed・診断との不一致を WARNING にする）
- `exports/notifications/actionable/history/YYYY-MM-DD.json`: その日の実行を足していく
- `exports/notifications/actionable/state.json`: 台帳（商品ごとの状態・通知済みの組み合わせ）
- 配信先の URL・トークンは記録しない。マイページ（一般向け）には出さない（送っていない通知を「通知」として見せない）。
  運営者向けの「通知」に件数と候補の商品・状態の変化だけを出す（組み合わせの識別子・URL は出さない）

## 8. レビュー・監査の指摘（対応済み）

- High（レビュー・最終確認）: 抽選 → 一般販売 → 同じ抽選 で同じ受付を再通知 → 通知済みの受付の集合
- Medium（監査・最終確認）: 抽選と在庫ありの行き来で在庫ありを再通知 → 同じ受付の抑制で一般販売の記録を消さない
- High（レビュー）: 1回の CI で LP の生成が2回（買取のプレ値のジョブの途中・本来の生成）走り、先の判定が台帳を書いて後の候補が
  消える → 通知は generate-daily-lp の生成だけ（#855 で検査）
- Medium（監査）: 台帳に無い商品が利益だけの変化で候補になる → 商品ごとの基準日
- Medium（レビュー）: 抽選の受付終了で re-arm して同じ受付を再通知 → 受付終了では re-arm しない
- Low: 受付の識別の書式・できる → できる・配信の直前の時刻・失敗時の latest.json・指標の項目・秘密の値の形（Discord の
  API の版・Slack・Bearer の行）・NaN の利益・診断に失敗した実行の記録・配信できなかった通知の出し直し・抽選から一般販売

## 9. 残している点（Low）

- 確定の利益から外れている間の在庫の変化は台帳に入らない（レビュー M-1・監査 M-1 の両立）。利益から外れて戻ったときは、その商品の
  基準日として通知しない。利益の変化だけで「購入可能になりました」を出さないことを優先し、外れている間に在庫切れ → 在庫ありが
  あった場合の通知は取りこぼす（誤通知より取りこぼし側に倒す。判定の材料が診断に無い）。診断の行が1件も無い実行（利益ルートの
  一時的な欠けなど）では台帳を変えない。記録だけした件数は latest.json の baseline_recorded
- 受付の識別で、日付だけの締切と 0:00 の締切は同じになる（実害は確認していない）
- 同じ抽選でも締切が延びると、別の受付として通知する（新しい締切を知らせる意味もあるので残す。抑えるなら識別を「商品 ID|開始」にする）
- 通知の生成の失敗は deploy-check #855 で WARNING（内部用の dry-run なので LP の公開は止めない。送信・dry-run でない・誤った候補は ERROR）
- deploy-check が失敗した実行では台帳がコミットされない（次の実行で同じ候補をもう一度計画する。dry-run の今は履歴が重なるだけ。
  送信を有効にする前に、台帳の保存を公開と切り離すか、受け側で識別子による重複の排除が要る）
- 秘密の値の検査は形の決まったもの（Discord・Telegram・Slack の URL、Authorization: Bearer の行）だけ。形の無いトークン単体は検出できない
  （通知の処理は環境変数を読まず、出力するのは配信先の名前だけ）
- 外部への送信の関数（Discord・Telegram）は接続していない（ユーザーの許可の後の作業）
- 一覧・HOME の件数は1日数回の生成時の判定（閲覧時は期限で落とすだけ）
